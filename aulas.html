Módulo 1 · Fundamentos

O que é monitoramento e por que usar Zabbix

Monitorar é transformar o comportamento de sistemas em dados observáveis. O Zabbix coleta métricas, avalia condições e mostra quando algo sai do esperado.

Disponibilidade indica se um serviço responde. Desempenho mostra quanto tempo e recurso consome. Capacidade informa quanto resta antes de saturar. Essas três perguntas orientam um projeto de monitoramento.

O Zabbix é software livre e suporta coletas com agentes, SNMP, HTTP e outros métodos. Uma boa implantação começa com objetivos, donos dos serviços e indicadores úteis; instalar a ferramenta é apenas o começo.

Mapa conceitual

Disponibilidade → desempenho → capacidade → decisão

Questão de revisão

Um servidor responde a ping mas sua aplicação está fora do ar. Por que monitorar somente ICMP não basta?

Ver resposta

ICMP comprova uma forma de conectividade, não o funcionamento da aplicação. Adicione uma verificação HTTP, serviço ou transação.

Módulo 2 · Fundamentos

Itens, hosts, templates e triggers

Host é a entidade monitorada: servidor, switch, hipervisor ou serviço. Item é a observação periódica, como memória disponível. Template reúne itens, triggers e outras configurações reutilizáveis.

Uma trigger avalia uma expressão e define se existe problema. Evento registra uma transição ou ocorrência. Ação pode notificar pessoas ou executar operações, com critérios e permissões explícitos.

Separe métricas de sintomas de métricas de causa. Disco livre é uma métrica; pouco espaço por tempo sustentado pode virar problema; limpeza automática não deve ser resposta indiscriminada.

Mapa conceitual

Host → item → valor → trigger → evento → ação

Questão de revisão

Uma trigger dispara por um pico de CPU de um segundo. Como melhorar?

Ver resposta

Avalie janela temporal, duração, criticidade e métricas complementares para reduzir falsos positivos.

Módulo 3 · Fundamentos

Coleta, descoberta e monitoramento distribuído

O Agent/Agent 2 lê métricas do sistema operacional. SNMP é comum para equipamentos de rede. HTTP agent e cenários web monitoram aplicações acessíveis via rede, enquanto APIs ampliam integrações.

Descoberta de baixo nível (LLD) cria automaticamente itens e triggers para recursos variáveis, como discos e interfaces. Prototypes definem o modelo para os recursos descobertos.

Proxy coleta em locais remotos e encaminha dados ao servidor. Isso diminui dependência de conectividade permanente e organiza topologias distribuídas, mas exige planejar buffers, TLS e retenção.

Mapa conceitual

Agent / SNMP / HTTP / API → proxy (opcional) → server

Questão de revisão

Você tem 30 filiais conectadas por links instáveis. Qual componente pode concentrar coletas locais?

Ver resposta

Zabbix Proxy, com dimensionamento e comunicação segura ao servidor central.

Módulo 4 · Arquitetura

Arquitetura: Server, banco, Proxy, Agent e Frontend

O Zabbix Server coordena coletas, avaliações e processamento. O banco de dados persiste configuração, histórico, tendências e eventos. O frontend fornece consultas, dashboards e administração.

Agents e métodos sem agente alimentam o servidor diretamente ou por proxy. O frontend consulta os dados armazenados; não é substituto do serviço de coleta.

Desenhe fluxos de rede, portas, DNS e autenticação. Documente dependências compartilhadas: dois servidores não asseguram alta disponibilidade se dependem do mesmo banco sem redundância.

Mapa conceitual

Hosts → Proxy opcional → Zabbix Server ↔ SGBD ← Frontend

Questão de revisão

A interface abre mas não surgem dados recentes. Qual componente investigar além do frontend?

Ver resposta

Zabbix Server, conexão com banco, disponibilidade dos coletores e filas de processamento.

Módulo 5 · Arquitetura

Alta disponibilidade: conceitos e falhas

Alta disponibilidade busca reduzir indisponibilidade por falha, não eliminá-la totalmente. RTO é o tempo-alvo de recuperação; RPO é a perda de dados tolerada. Ambos orientam arquitetura e testes.

Um arranjo com dois nós de aplicação pode assumir serviço após falha, mas o banco, armazenamento, DNS, rede e energia também são pontos possíveis de falha.

Failover exige simulação: interrompa um nó em laboratório, observe eleição, continuidade de ingestão, acesso web e recuperação. Testes documentados valem mais que a palavra cluster.

Mapa conceitual

Nó A ↔ nó B → banco compartilhado → dependências críticas

Questão de revisão

O banco único cai e os dois nós de aplicação ficam no ar. O ambiente está altamente disponível?

Ver resposta

Não de ponta a ponta; o banco único é um ponto único de falha.

Módulo 6 · Planejamento

Inventário, requisitos e topologia

Antes de instalar, liste ativos, itens por ativo, períodos de coleta, quantidade de usuários, crescimento esperado e criticidade. Uma contagem de hosts isolada não determina a carga.

Considere CPU, RAM, disco, latência do SGBD, rede e manutenção. Ambientes com muitos itens de alta frequência geram volume muito superior aos que coletam poucos itens a cada cinco minutos.

Produza um diagrama com funções separadas: bancos, servidores, proxies, frontend, acesso administrativo e redes de monitoração. Defina backups, restauração e atualização antes de entrar em produção.

Mapa conceitual

Inventário → itens/frequência → VPS → retenção → capacidade

Questão de revisão

O que costuma afetar mais o crescimento do histórico: número de dashboards ou valores coletados por segundo?

Ver resposta

A taxa de valores armazenados e a retenção costumam dominar o crescimento do histórico.

Módulo 7 · Planejamento

VPS: valores por segundo

VPS significa novos valores processados por segundo. Em cenário simplificado com itens de mesmo intervalo, VPS = quantidade de itens ÷ intervalo em segundos.

Exemplo: 24.000 itens coletados a cada 300 segundos produzem aproximadamente 80 valores por segundo. Em produção, calcule grupos de itens por frequência e some os resultados.

O VPS ajuda a estimar escrita no banco e capacidade. Não confunda itens configurados com itens realmente suportados/ativos nem considere o número estimado como benchmark garantido.

Mapa conceitual

24.000 itens ÷ 300 s = 80 VPS

Questão de revisão

Se dobrar a frequência de coleta (de 300 s para 150 s), o que acontece com o VPS?

Ver resposta

Ele aproximadamente dobra, mantidas as demais condições.

Módulo 8 · Planejamento

Histórico, trends e estimativa de disco

History retém valores coletados em detalhe. Trends agregam métricas numéricas em janelas horárias, permitindo consultas de longo prazo com menos registros.

Estimativa didática do livro: histórico ≈ dias × 86.400 × VPS × bytes médios por valor. Para 7 dias, 80 VPS e 90 bytes: cerca de 4,35 GB decimais de dados brutos estimados.

Não trate esse número como tamanho final do banco: índices, metadados, eventos, tipos de dado, compressão e implementação podem alterar muito o consumo. Monitore crescimento real e reserve folga.

Mapa conceitual

VPS → history (detalhe) + trends (agregação) → disco

Questão de revisão

Para investigar um pico de 30 segundos de 90 dias atrás, trends horárias bastam?

Ver resposta

Normalmente não; agregações horárias não preservam todos os detalhes de picos curtos.

Módulo 9 · Banco de dados

MariaDB/MySQL: função, implantação e contas

O SGBD mantém configurações e telemetria. Defina versão compatível, parâmetros de conexão, serviço gerenciado, diretórios e backup. O livro usa MariaDB/MySQL como cenário de estudo.

Crie um usuário de aplicação próprio, limite privilégios e origens permitidas e proteja as credenciais. Contas administrativas não devem servir para a conexão cotidiana do Zabbix.

O procedimento de instalação varia com distribuição e versão. Execute exemplos de comandos somente em laboratório e confirme-os na documentação específica do seu stack antes de produção.

Mapa conceitual

Servidor Zabbix → usuário de aplicação → SGBD

Questão de revisão

Por que usar uma conta de banco específica para o Zabbix?

Ver resposta

Por isolamento, auditoria, revogação e menor exposição das credenciais administrativas.

Módulo 10 · Banco de dados

Segurança do SGBD e criptografia TLS

Hardening envolve remover contas e bases de teste desnecessárias, restringir acessos remotos e auditar permissões. Serviços expostos devem ser minimizados.

TLS protege o tráfego contra leitura e alteração em trânsito. Não basta habilitar criptografia: certificados, nomes de host e cadeia de confiança precisam ser verificados pelo cliente.

Armazene material privado com permissões adequadas, planeje renovação e valide conexões com TLS antes de remover acesso legado. Faça alterações com janela e possibilidade de retorno.

Mapa conceitual

Cliente → TLS validado → MySQL/MariaDB

Questão de revisão

TLS sem validar certificado protege integralmente contra servidor falso?

Ver resposta

Não; a validação da identidade do servidor é essencial contra ataques de intermediário.

Módulo 11 · Performance

Tuning de banco: buffer pool, consultas e I/O

O InnoDB Buffer Pool guarda páginas de dados e índices em memória, reduzindo leituras em disco. Um valor insuficiente provoca mais I/O; um valor excessivo pressiona o restante da máquina.

Analise latência de disco, escrita, cache hit, CPU, conexões e queries antes de alterar variáveis. Mudanças devem ser graduais e mensuráveis.

Ajustes de memória, logs e checkpoint dependem do SGBD, tamanho do banco e características de hardware. Não aplique números de outro ambiente como receita universal.

Mapa conceitual

Carga → métricas do SGBD → hipótese → ajuste → validação

Questão de revisão

Um banco apresenta alta latência. Aumentar buffer pool é sempre a solução?

Ver resposta

Não. Investigue I/O, consultas, contenção, checkpoint, memória e padrões de acesso.

Módulo 12 · Performance

Linux: swap, I/O e limites

O sistema operacional influencia o desempenho do monitoramento. Observe swap, pressão de memória, latência de armazenamento, arquivos abertos e limites de processos.

Swappiness representa a tendência do kernel a usar swap sob certas condições. Ajustes cegos podem piorar comportamentos; use métricas do ambiente e teste antes de persistir mudanças.

Mantenha o sistema atualizado, sincronizado no tempo e com logs acessíveis. Mudanças de sysctl ou limites devem ser registradas e reversíveis.

Mapa conceitual

Métricas → gargalo → ajuste pequeno → medir

Questão de revisão

Se a máquina usa swap mas tem memória disponível, isso prova problema?

Ver resposta

Não necessariamente; avalie pressão real de memória e atividade de swap antes de agir.

Módulo 13 · Implantação

Instalando Zabbix Server e frontend

Uma implantação começa pela seleção de versão compatível, repositórios confiáveis e dependências. O banco é preparado e a estrutura inicial importada conforme o procedimento da versão escolhida.

Configure credenciais, hostname, parâmetros do servidor e frontend com permissões restritas. Inicie serviços e valide conectividade e logs antes de configurar itens complexos.

O assistente web finaliza configuração visual e exige ajustes corretos de banco, idioma e fuso horário. Faça uma checagem de saúde após cada etapa, em vez de executar tudo sem validar.

Mapa conceitual

Repositório → SGBD → Zabbix Server → Frontend → validação

Questão de revisão

Qual é o primeiro teste depois de iniciar o serviço?

Ver resposta

Verificar status/log do serviço, conectividade com SGBD e depois acesso ao frontend.

Módulo 14 · Alta disponibilidade

Keepalived e IP virtual no frontend

Keepalived pode controlar a posse de um IP virtual entre nós de frontend. Isso facilita a continuidade de acesso ao endereço, desde que rede e verificações estejam bem configuradas.

Um VIP não substitui o mecanismo de HA do Zabbix Server. São camadas diferentes: acesso web e processamento de monitoramento. O comportamento de cada uma deve ser testado separadamente.

É importante evitar split-brain, checar saúde efetiva da aplicação e assegurar coerência entre configuração, banco e nós. Um teste apenas de ping ao VIP não prova integridade de serviço.

Mapa conceitual

Usuário → VIP → frontend A ou B → backend

Questão de revisão

Um VIP migrou corretamente, mas a interface retorna erro 500. O failover foi bem-sucedido?

Ver resposta

A conectividade do VIP funcionou, mas a disponibilidade da aplicação ainda falhou.

Módulo 15 · Alta disponibilidade

Testes de failover e recuperação

Defina um conjunto de cenários: desligamento planejado de um nó, falha inesperada, retorno do nó, perda de rede e manutenção do banco.

Registre tempo de detecção, tempo de recuperação, perda de valores e acesso ao frontend. Verifique se a coleta continua e se eventos de indisponibilidade aparecem corretamente.

Não provoque falhas em produção sem autorização, janela e plano de recuperação. Exercícios controlados de laboratório trazem evidências e revelam dependências ocultas.

Mapa conceitual

Injetar falha → medir → restaurar → revisar

Questão de revisão

Por que testar o retorno do nó é tão importante quanto a saída?

Ver resposta

Porque a reintegração pode causar conflito de papéis, instabilidade ou interrupção adicional.

Módulo 16 · Segurança

HTTPS no Apache e proteção do frontend

HTTPS cifra o tráfego entre navegador e frontend, reduzindo exposição de sessões e credenciais. Use certificado confiável e nome DNS correspondente.

Configure redirecionamento HTTPS, renovações de certificado, controles de acesso, atualizações e permissões administrativas. Segurança também depende das contas e integrações.

Faça a distinção entre TLS do navegador, TLS do banco e criptografia dos agentes/proxies: são enlaces diferentes e precisam de políticas próprias.

Mapa conceitual

Navegador ↔ HTTPS ↔ Frontend ↔ DB/Server

Questão de revisão

Ativar HTTPS no Apache criptografa automaticamente a comunicação do agente?

Ver resposta

Não. Cada conexão necessita sua própria configuração de segurança.

Módulo 17 · Dados

Particionamento MySQL: ganhos e riscos

Particionar tabelas muito grandes pode facilitar manutenção e descarte de faixas antigas de dados, dependendo do SGBD e do esquema usado.

Há custos: complexidade, compatibilidade, procedimentos agendados e risco operacional. O livro apresenta stored procedures como uma estratégia histórica para history/trends.

Antes de particionar, verifique suporte oficial, mecanismo de armazenamento, versão e alternativas de retenção. Nunca aplique scripts antigos diretamente a um banco de produção sem testes e backup restaurável.

Mapa conceitual

Tabela → partições por período → retenção controlada

Questão de revisão

Particionamento elimina a necessidade de monitorar espaço em disco?

Ver resposta

Não. Capacidade e retenção continuam exigindo monitoramento.

Módulo 18 · Dados

Housekeeping e políticas de retenção

Housekeeping remove informações antigas de acordo com a política definida. Valores de history, trends e eventos possuem utilidades e períodos diferentes.

Uma retenção muito curta prejudica investigações; uma longa aumenta custos. Negocie requisitos técnicos, regulatórios e operacionais com os responsáveis pela infraestrutura.

Documente cada período e acompanhe sua efetividade. A retenção deve ser avaliada junto do crescimento medido do banco, não isoladamente.

Mapa conceitual

Necessidade de análise → retenção → custo → revisão

Questão de revisão

Qual é o risco de remover history muito cedo?

Ver resposta

Perder a granularidade necessária para investigar ocorrências recentes ou intermitentes.

Módulo 19 · Operação

Diagnóstico de problemas no Zabbix

Comece separando ausência de coleta, atraso de coleta, falha de avaliação e falha apenas na visualização. Essas situações parecem iguais ao usuário, mas têm origens diferentes.

Cheque serviço Server, disponibilidade do banco, proxy, filas, itens não suportados, comunicação do agente, DNS e certificados. Registre horários para correlacionar eventos.

Uma hipótese só vira causa confirmada quando existem evidências e validação. Em NOC, descreva impacto, evidências e próximo responsável; evite corrigir por tentativa em produção.

Mapa conceitual

Sintoma → camada → evidência → correção → validação

Questão de revisão

Itens pararam após alteração de certificado. Qual hipótese merece teste prioritário?

Ver resposta

Falha de negociação TLS, confiança ou identidade entre os componentes.

Módulo 20 · Operação

Projeto final: desenhe um Zabbix resiliente

Cenário: 400 VMs em três provedores, dois sites remotos e um NOC central. Defina o que coletar, quais sistemas são críticos, frequência de cada classe e metas de retenção.

Desenhe arquitetura com Zabbix Server, banco, frontend, proxies, backups e política de acesso. Calcule VPS por classe de item e antecipe crescimento.

Escreva uma estratégia de restauração e cinco testes de falha. O resultado esperado é uma documentação replicável, não apenas a instalação funcionando em um único dia.

Mapa conceitual

Requisitos → arquitetura → capacidade → segurança → testes

Questão de revisão

Qual evidência comprova que o projeto atinge a meta de recuperação?

Ver resposta

Relatório de testes com tempos medidos, integridade dos dados e validação do serviço.
